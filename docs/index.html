📚 Design documents

docviewer: a Go practice project, a resilient read-side aggregator

📚

Design documents for docviewer, a Go practice project: a read-side aggregator that takes a vehicle identification number and returns one paged list of documents from two upstream systems, merged newest first, with partial-failure semantics, a stable cursor, retries and circuit breakers, and OpenTelemetry throughout. The design was written before the code, then kept in step with it. The code, with its README (build, run, test), is on the README.

Read in order

  1. PRD, the requirements: what the viewer does and how it behaves, with no technology in it: the scenario, the requirements, the assumptions that fill gaps (A-01 to A-08), and the acceptance criteria (AC-01 to AC-12) that the end-to-end tests are named after.
  2. HLD, the high-level design: components, API, paging cursor, failure handling, observability, security and the decisions (D-01 to D-14) with their reasons.
  3. LLD, the low-level design: repository layout, packages, core types, key logic, configuration, mock systems, test plan and the implementation order.

How to read the identifiers

  • A-nn assumptions (PRD section 5), AC-nn acceptance criteria (PRD section 6), H-nn things a new source system must satisfy (HLD section 15), D-nn decisions (HLD section 16).
  • The Go code cites these identifiers in comments and test names, so a requirement can be traced to the test that proves it.
