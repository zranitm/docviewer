1. Scope

  • A stateless backend service for the Unified Document Viewer.
  • The two upstream systems are external and mocked; their contracts are in section 5.
  • The client is stubbed with an OpenAPI spec and cURL examples; the UI is out of scope.

2. Architecture

3. Components

ComponentRole
Document APIValidates the VIN, page size and cursor; shapes the page and the next cursor.
AggregatorFetches a page from every source in parallel, interleaves newest first, cuts to the page size, computes the next cursor.
Source adaptersOne per system: turn its client into a pageable source (positions to paging parameters, errors to failure types, wire models to the canonical document).
Upstream clientsOne per system: its endpoints and wire models, no domain logic, so other code can reuse them.
Resilience layerA circuit breaker and a bounded retry in each client's HTTP transport, so every caller of a client gets them.
ObservabilityOne grafana/otel-lgtm container: traces, metrics and logs over OTLP, viewed in Grafana.

4. Data flow

  1. Each unfinished source is asked for limit documents after its position (from the newest on the first page), in parallel.
  2. Results are interleaved newest first and cut to limit.
  3. Each source's new position is the last document it had on the page, so cut-off documents come back next time and nothing is skipped.
  4. next_cursor is null once every source is done or unavailable.

When a source fails (D-13), the page is built from the others and the failed source is named. Healthy calls are never cancelled.

  • Transient (timeout, connection error, 5xx, 429, open breaker): position stays put; the next page retries. Its documents may arrive out of date order (PRD A-05).
  • Permanent (400, 401, 403, 422, or a response over 1 MB): marked unavailable, not called again; the list ends without it.
  • 404: no documents; marked done.
  • Stalled: a source that answers ok with no usable documents, says it has more, and gives no position to skip to would be asked the same question forever. The page reports it ok (it did answer) but the next cursor marks it unavailable, so the list ends rather than loops. This is the one way a source goes ok on one page and unavailable on the next without a failed call.
  • Nothing answered (every source asked on this page failed): 502 with per-source statuses when retrying may help (any failure was transient) or when no document has been shown yet (every source still at its start). Once documents have been shown and every remaining source has failed permanently, the list is simply over: a terminal 200 with no documents, those sources unavailable and next_cursor null, so the client is never left holding a cursor that can only fail.

5. API

EndpointPurpose
GET /v1/vehicles/{vin}/documents?limit=...&cursor=...One page of consolidated documents for a VIN
GET /healthzLiveness
GET /readyzReadiness: started and not shutting down
  • limit defaults to 20, max 100.
  • Pass the previous next_cursor to get the next page.
  • X-Trace-Id response header: the request's W3C trace ID (32 lower-case hex characters), on every traced response, success or error (200, 400, 502, 500 alike). It names the request's trace in Tempo and its log lines, which carry the same trace_id, so a reported failure can be matched to what the service saw. The service always samples its own spans, so an inbound traceparent can hand it a trace ID but can't turn export off, and the header is only written when the span is sampled: an ID in the header always resolves to a trace. CORS exposes it, so the demo UI appends "trace <id>" to its failure notices. The ID is random, so it carries no PII. The health probes aren't traced and don't carry it.

7. Paging cursor

The cursor records where a page ended, so the service stores nothing. next_cursor is base64url-encoded JSON, opaque to the client:

{
  "v": 1,
  "query": { "vin": "1M8GDM9AXKP042788" },
  "streams": {
    "sales":   { "state": "after", "key": ["2024-03-02T00:00:00Z", "sales:S-1002"] },
    "service": { "state": "done" }
  }
}
  • v is the format version.
  • query holds everything that defines the list; today, just the VIN. It must equal the request's query.
  • streams has one entry per source, always, in one of four states, with key holding the sort key of the last item returned:
StateMeaningCalled on the next page?
startNothing returned yetYes, from the beginning
after, with key = [date, ID]The last document from this source already returnedYes, for documents after it
doneNothing more, or the source answered 404No
unavailableFailed permanently (400, 401, 403, 422, or over 1 MB)No

How it moves

  • Every unfinished source is asked for the full limit, never a share (section 11).
  • Every configured source always has an entry (start until it returns something), so a missing entry can only mean a source added since the cursor was issued.
  • The key moves to the source's last document on the page; it stays put if none made it or the call failed transiently.

Why the key is a date and an ID

  • Systems order by date, then ID, so a position needs both.
  • IDs don't follow dates (backfilled records, text IDs), and the ID breaks same-date ties.
  • It still works if the anchor document is deleted.

Validation (400)

  • invalid_cursor: doesn't decode; unknown version or field; a malformed key; or a query that doesn't match the request (another VIN, say).
  • cursor_outdated: lacks a source added since. That source could only start from its newest documents, which would appear after older ones already shown.
  • Entries for removed sources are ignored; the rest keep their order.

Designed to evolve

  • New list dimensions go in query. An order or a filter is added as a field with a default; a cursor without it means the default, so old cursors stay valid.
  • The key's layout follows the order, so a new sort needs no new cursor fields: [date, id] today, [title, id] for a title sort.
  • Decoding is strict. Unknown fields are refused, so during a rolling deploy older code rejects a cursor written by newer code (the client restarts) instead of half-reading it.
  • v changes only when an existing field's meaning changes: the ID format, the key layout, or the encoding (adding a signature, say). An unknown v is rejected, not misread.
  • Sources come and go without a version change: an added one makes old cursors outdated; a removed one is ignored.

A future cursor with oldest-first order and a filter, same format:

{
  "v": 1,
  "query": { "vin": "1M8GDM9AXKP042788", "order": "oldest", "filter": { "type": "repair_order" } },
  "streams": {
    "sales":   { "state": "after", "key": ["2024-03-02T00:00:00Z", "sales:S-1002"] },
    "service": { "state": "unavailable" }
  }
}

Properties

  • Stateless; never expires.
  • Not secret: the query and positions only.
  • Independent of limit, so the page size can change between pages.

Changes while paging

  • Added with a date older than the cursor's position: appears on a later page.
  • Added at or above it (usually a new document dated today): only on a new search.
  • Deleted before the cursor reaches it: doesn't appear.

Known limit: during a long transient outage, "load more" stays open; the client decides when to stop.

8. Data and state

  • Canonical document: id, source, type, title, summary (optional), issued_at, url, checksum (optional).
  • No de-duplication in v1 (D-11): a file held by both systems appears once per system. Checksums and the sources list are kept for the planned index (section 14).
  • Stateless: every page is composed live from the systems of record, so cursors match what they hold and any instance can serve any page.
  • No database (D-02). This design deliberately has none. Every candidate use was weighed and dropped:

    A database added only to meet the wording would have no job; the checksum index (section 14) would be its first real one.

    • saved results: break cursor consistency;
    • audit table or recent searches: need sign-in to know who;
    • source registry: a new kind of system needs code anyway;
    • API-key clients with an access log: bring authentication into scope;
    • server-side paging sessions: make the service stateful.

10. Reliability

  • Deadlines: 2s per source, 3s per request (PRD A-07), propagated to upstream calls.
  • Independent sources: one failing never cancels another; failures map per D-13 (section 4).
  • Circuit breaker: per source; opens after 5 consecutive failures for 30s, then lets a probe through. Client cancellations and permanent rejections don't count.
  • Retries: at most one, with jitter, only for transient errors and only if the deadline allows. Safe: the same position gives the same page.
  • Coalescing: concurrent requests for the same VIN, cursor and page size share one fan-out; one client disconnecting doesn't fail the others.
  • Graceful shutdown: in-flight requests drain on SIGTERM.

11. Scalability and performance

  • Horizontal: stateless, so it scales behind a load balancer; upstream connections are pooled.
  • Latency: bounded by the slowest source within its deadline, not the sum.
  • Cost per page: at most limit documents per source, however many the vehicle has.
  • Full limit per source: splitting would break the order, so N sources fetch N × limit to return limit. The cut-off part is fetched again next page: the price of staying stateless.
  • New systems: one adapter and one stream entry, no API change (section 15).

12. Observability

  • Logs: slog to stdout as JSON and to Loki; one line per request and per source call, with trace ID, source, status and duration; redacted (section 13).
  • Metrics (OpenTelemetry SDK; instruments are dotted OTel names with units, such as docviewer.http.request.duration in seconds, shown here as Prometheus renders them):

  • Traces: a span per request and per source call; overlapping source spans in Tempo show the fetches running in parallel. The request's trace ID is returned to the client in X-Trace-Id (section 5), so a reported failure leads straight to its trace and log lines.
  • Alerts, in production: error or timeout ratio per source; p95 latency near the 3s deadline; a breaker open for minutes.
  • Local vs production: the all-in-one image is for development and demos. Production would run Tempo, Loki, Prometheus and Grafana separately, with Grafana Alloy collecting.

13. Security and privacy

  • Authentication: out of scope (PRD A-08); the service would sit behind the dealership platform's gateway.
  • Input: the VIN is validated before any upstream call; upstream URLs come from configuration, never from input.
  • PII in telemetry (LLD section 8): VINs can be personal data, and document fields or upstream bodies can hold customer names. One redaction component covers logs and traces:

    Metrics never label by VIN. Responses aren't redacted, since the caller is assumed authorised.

    • VINs masked to their last 4 characters;
    • route templates, never the raw path or query (both carry the VIN);
    • no document fields or upstream bodies;
    • on by default; telemetry.redact.enabled turns it off at start for local debugging, with a warning.
  • Cursor: opaque but not secret; malformed or foreign-VIN cursors get 400.
  • Upstream limits: timeouts, and a 1 MB cap per response; anything larger is a permanent failure (D-13).
  • CORS: allowed origins come from server.cors_origins, empty by default.

14. Future enhancements

Cross-system de-duplication with a checksum index

Goal: show a file held by both systems once, wherever its copies fall in the list.

Mechanism

  • Requires: each system exposes a SHA-256 checksum per file (the mocks do). Without one, the service would have to download and hash files itself (slow, costly), or those documents wouldn't merge.
  • Store: Postgres doc_index(source, doc_id, vin, checksum, issued_at, url, last_seen_at), key (source, doc_id), index (vin, checksum).
  • Write: a background writer upserts every fetched document, including over-fetched ones, and skips unchanged rows seen recently. Pages never wait on it.
  • Read: after the upstream calls, WHERE vin = $1 AND checksum = ANY($2) for the page's checksums; index seeks only, about 1–2 ms.
  • Leader: the list order is fixed, so the copy that sorts first lists every known copy in sources; a later copy gets duplicate_of with the leader's ID.

Example: A (Sales) and B (Service) are the same file.

Page 1Page 3
On the pageAB
Index lookup findsBA, which sorts first
ReturnedA, also listing B's linkB with duplicate_of: "sales:S-1002"
ClientShows AFolds B into A

Safety

  • The client decides, because only it knows what it has rendered; nothing is hidden server-side.
  • If the leader was deleted or added behind the cursor, the copy still shows.
  • A client ignoring the mark behaves like v1.
  • A stale index costs at worst a dead link, never a lost document.

Limits and cost

  • On a VIN's first search, the earlier copy can't list an unseen twin, but the later copy is still caught; only same-page twins slip through.
  • Freshness: rows change only when re-fetched; last_seen_at with an expiry retires old ones. Real freshness would need change events, which we don't assume.
  • About 300 bytes per document; a soft dependency; a migration, a store, the writer and an expiry job.
  • If latency ever mattered, a write-time twins(vin, checksum) table would let the lookup run alongside the upstream calls.

15. Adding a source

The aggregator works over a list of sources, so a new system plugs in without changing the aggregator, the cursor format or the API.

Steps

  1. Check the assumptions (section 6): queried by VIN, keyset paging newest first, a stable ID and date per document. A checksum is needed only for the future de-duplication (section 14).
  2. Write a client (endpoints, wire models) and an adapter implementing Source (Name, FetchPage) that:
    • calls the system from the given position;
    • maps its schema to the canonical document and its statuses per D-13;
    • enforces the 1 MB cap and prefixes IDs with the source name.
  3. Wire it in: one line in the source registry and one entry under sources.upstreams in configuration (base URL and timeout). The existing wiring loop gives its client the tracing and resilience transport; no existing code changes.
  4. Test it: mapping, status mapping, and paging with same-date ties and its own ID order; add a mock to the test harness (LLD section 10).
  5. Update the docs: the contracts table (section 5) and the LLD mapping.

When it ships

  • Old cursors lack the new source, so they get cursor_outdated and clients restart from page 1 (section 7).
  • During a rolling deploy, old instances ignore the new entry, but a client bouncing between old and new instances may be asked to restart more than once.
  • Each page fetches up to limit from one more source (section 11).
  • Telemetry picks it up through the source label; only the dashboard needs updating.

If the system doesn't fit

  • Needs an ID lookup first: do it inside the adapter, within the source's timeout (H-01).
  • Only page numbers: translate in the adapter, accepting possible skips or repeats (H-02).
  • No VIN query or no date order: can't be paged correctly without fetching everything; needs a different integration, such as the system exporting its data.
